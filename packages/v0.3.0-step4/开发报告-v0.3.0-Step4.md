## 3. Agent 架构

```
商品数据 (MICPageSchema + images)
        │
        ▼
AgentOrchestrator
  1. ProductIdentityAgent   (capability: vision)
  2. KeywordAgent           (capability: keyword)
  3. ContentAgent           (capability: content)
  4. VerificationAgent      (capability: verification)
        │
        ▼
AISuggestion[]   全部 PENDING
        │
用户点击「接受」
        │
approveSuggestion → applySuggestion → convertMICPageToBuilder → replacePage
```

失败码（写入 warnings，不换模型）：

- `MODEL_UNAVAILABLE`
- `ROLE_CAPABILITY_MISMATCH`（例如 DeepSeek 被指派做 vision）
- `TIMEOUT`
- `EMPTY_RESPONSE`

## 4. 模型接入方式

不写死模型名。用户按能力绑定 `provider:model`：

```
VITE_AGENT_VISION=gemini:your-vision-model
VITE_AGENT_KEYWORD=deepseek:your-keyword-model
VITE_AGENT_CONTENT=openai:your-content-model
VITE_AGENT_VERIFICATION=claude:your-verify-model
```

密钥（按品牌，与模型名无关）：

`VITE_OPENAI_API_KEY` / `VITE_GEMINI_API_KEY` / `VITE_DEEPSEEK_API_KEY` / `VITE_KIMI_API_KEY` / `VITE_ANTHROPIC_API_KEY`

例：Vision=Gemini，Content=GPT，Keyword=DeepSeek —— 允许。Vision 指派 DeepSeek —— `ROLE_CAPABILITY_MISMATCH`，不会改去 Gemini。

HTTP：OpenAI 兼容（OpenAI / DeepSeek / Kimi）、Gemini `generateContent`、Claude `messages`。

## 7. Step 5 建议

1. 把 assignment UI 做成 Suggest 面板里的四格选择（Vision/Keyword/Content/Verify），不要写死品牌。
2. 给 HTTP provider 加重试与 token 计量，失败仍只 warning。
3. Identity 的 vision 真正走多模态 image_url / inline_data，而不是把 URL 拼进 prompt。
4. Verification 的 BLOCKED 项可在 UI 显示为只读「已拦截」，仍不可一键 apply。
5. 不要把 Agent 输出写进 History Command；继续走用户确认后的 `replacePage`。
